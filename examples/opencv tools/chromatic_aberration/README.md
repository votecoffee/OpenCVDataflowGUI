# Calibrated color-fringe correction

Open **chromatic_aberration.json** and press **Run once**. No plugin is needed.
The original synthetic 16-bit part has blue/red fringes around bores and edges.
The native JSON calibration is loaded beside the project, then OpenCV corrects
R/B onto green's unchanged pixel grid. The result appears in the filmstrip.

Inspect these results:

| Block/output | Expected result |
| --- | --- |
| Fringe error before correction | **30,975** raw-unit maximum error against the independent ideal image. |
| Exact corrected pixels | Maximum absolute error **0** on supported pixels. |
| Correction → Valid mask | Rectangle `[x=3, y=1, width=235, height=157]`. |
| Correction → Report | **36,895 / 38,400** supported pixels, approximately **96.08%**. |
| Correction → Image | Original uint16 RGB depth/order retained. |

`defined_model.json` uses editable coefficients instead of loading the file.
`insufficient_support.json` intentionally requires 100% support: correction
fails, retains masks/report and emits no corrected image or final filmstrip
image. This is expected failure behavior.

`expected.json` records the independent grid, displacements, support rectangle
and zero-error requirement. `build_example.py` regenerates every image, model
and project using only NumPy/OpenCV and the application's graph API. The native
displacement convention is B(-2,+1), R(+3,-2); source channels are generated by
direct integer indexing rather than using the correction implementation.

The image, calibration, generator and graphs are original OpenCVDataflowGUI
work under the repository MIT license. The canvas includes the same attribution.
Algorithm reference: [OpenCV chromatic correction](https://docs.opencv.org/5.0/main_modules/photo_ca_correction.html).
See [model, support and payload contracts](../../../docs/chromatic-aberration.md).
This supplied synthetic calibration qualifies the software path; real camera
coefficients must be fitted from suitable lens-specific captures.
